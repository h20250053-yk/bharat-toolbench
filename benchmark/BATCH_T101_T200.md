# Batch T101-T200: the 20-tool stage (benchmark 3.0)

Source of truth: `benchmark/batch_t101_t200.py` (specs and the text in all five languages), solvers in `benchmark/solvers_t101_t200.py`,
independent oracle in `benchmark/oracle_t101_t200.py`, service rules in `environment/data/services.json` (generated by
`environment/build_services.py`). Every non-English prompt is a Claude-generated draft that still needs a human check.

## Why these tools

The first two stages cover finding, booking, cancelling and waiting for a seat. The third stage adds the services a passenger actually uses
around a journey, chosen because each one overlaps with a tool the model already has, so the model must pick the right one and respect an
irreversible order of actions:

| Tool | Overlaps with | What the task tests |
|---|---|---|
| `check_tatkal_availability` / `book_tatkal_ticket` | `check_availability` / `book_ticket` / `join_waitlist` | a second quota with its own window, price and rules (no concession); fallback chains general -> Tatkal -> waitlist |
| `get_berth_availability` | `check_availability` | berth type (lower, side lower, upper) as a booking condition; CC has no berths |
| `get_platform_info` | `get_train_details` | platform and coach order at a stop; 'not a stop' must be detected |
| `change_boarding_point` | `get_train_details` (stop times) | a state change with a 24-hour deadline; preview without changing |
| `order_meal` | `get_live_train_status` | delivery depends on the LIVE arrival (lead time, serving hours, passed stations) |
| `file_tdr` | `get_cancellation_refund` / `cancel_ticket` | the better of two refund routes; eligibility without acting |
| `raise_complaint` | `file_tdr` | mapping free text to a category; only during the journey; AC only in AC classes |

Only the Tatkal opening times (AC 10:00, sleeper 11:00 on the day before departure) follow the real Indian Railways rule; every other rule
and number is synthetic (`benchmark/data_provenance.md`).

## Design rules (same as T76-T100)

* One solver kind per task; each solver asserts the situation it relies on (sold out, window not open, too late, not eligible ...), so a
  fixture change cannot silently change a task.
* Gold for T01-T100 is byte-identical after this stage (checked when the stage was built).
* Explicit prohibitions only where the prompt forbids something in words: T104 'not the general quota', T109 "don't put her on the
  waitlist", T140 "don't change the booking", T175 "Don't file it yet", T196 "Don't book anything".
* Equivalent observations (another call that proves the same fact, e.g. a booking status showing WAITLISTED instead of the rejected
  change) are listed in the spec and in `evaluation/scorer.EQUIVALENT_PATHS`.
* The requested facts are checked as structured `answer_values` (`evaluation/scorer.STRUCTURED_VALUE_CHECKS`); new state changes
  (Tatkal bookings, boarding changes, meal orders, TDRs, complaints) are compared in `final_state.expected_effects`.
* Each stage is offered only its own tools: these tasks get all twenty.

Tool letters: R resolve, S search, D details, A availability, F fare, B book, P PNR status, Q refund quote, X cancel, W waitlist, L live
status, C concession, K Tatkal check, T Tatkal book, H berths, N platform, G boarding change, M meal, Z TDR, E complaint. `?` = optional call,
`!CODE` = the call is expected to fail with that error.

## Known limits

* Berths are reported for the general quota's free seats; `book_ticket` does not assign a berth type, so a 'lower berth' condition is a
  condition on availability, not a guaranteed allocation.
* Several tasks reuse the same few running trains (BTB103, BTB110, BTB122 and the PNRs on them) because only those runs are in progress at
  the pinned time; each task still has a different reasoning step (checked by `benchmark/semantic_overlap.py`).
* Platforms and coach order are synthetic and constant per (train, station).
