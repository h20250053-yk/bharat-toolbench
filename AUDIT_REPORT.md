## 2. Critical

### C-01: default `--languages` omits Gujarati
- **File:** `evaluation/run_pilot.py:54` (default `["en","hinglish","hi","mr"]`); `README.md` and `LOCAL_MODELS.md` commands do not pass the flag.
- **What is wrong:** `--split full` now means T01-T75, but without `--languages en hinglish hi mr gu` it runs 75 x 4 = 300 items and silently omits all Gujarati (75 items). A "375-item evaluation" would be wrong without any error.
- **Evidence:** `task_ids('full')` returns 75 tasks; with the default 4 languages `load_items` expects 300 (checked in a script). The default is plain code at line 54.
- **Proposed fix:** make the default all five languages (`["en","hinglish","hi","mr","gu"]`), and print the item count before the run starts. Update the README command examples.
- **Frozen/history:** no frozen data. Historical 200-item runs used `midsem` and are unaffected, but anyone re-running the old command would now get 375 items, so pass `--split midsem --languages en hinglish hi mr` explicitly in the old-run docs.

### C-02: analysis and provenance tools assume 200 items / 4 languages
- **Files:** `analysis/observe_run.py:31` (`LANGUAGES` has 4) and `:62` (`n = {"pilot": 5, "full": 50}[split]`, no `midsem` key); `analysis/format_recovery.py:413` (hard-coded 4 languages); `analysis/prerun_snapshot.py:25-26` (hashes only en/hinglish/hi/mr, not `gu.jsonl`), `:56` (`expected_items = len(task_ids(split)) * 4`), `:66` (`--split` choices only pilot/full).
- **What is wrong:** `run_pilot --split full` now means 75 tasks, but `observe_run` still thinks `full` is 50 tasks and has no Gujarati. For a 375-item run the integrity report would list 125+ rows as `unexpected_items` and mark `complete=False`; `--languages gu` is rejected by argparse; the prerun snapshot would record `expected_items: 300` and would not hash `gu.jsonl`, so the manifest could not detect a Gujarati change between runs. Without these tools the `analysis/REPRODUCE.md` procedure cannot be followed for new runs.
- **Evidence:** ran `expected_items('full', [4 langs])` -> 200 ids ending at `T50_mr`; `expected_items('midsem', ...)` -> `KeyError 'midsem'`; `task_ids('full')` -> 75 tasks. Code lines as above.
- **Proposed fix:** derive the task list from `run_pilot.task_ids(split)` and the language list from one shared constant (5 languages), add `midsem`, add `gu.jsonl` (and `human_review.json`) to `HASHED_FILES`, compute `expected_items` from the chosen languages. Keep the 200-item behaviour reachable through `--split midsem --languages en hinglish hi mr`. Add a test that `expected_items('full', ALL_5)` has 375 entries.
- **Frozen/history:** no frozen data. It must not change the output of the already-published analyses in `analysis/results/` (re-run them only into new folders); the existing tests in `tests/test_observe_run.py` encode the 200-item numbers and must keep passing for `midsem`.

### I-02: times with a day-part word and a 24-hour hour are dropped
- **File:** `evaluation/canonical.py:123-142` (`_MORNING`..`_NIGHT`, `_apply_part`) and `:145-173` (`times_in`).
- **What is wrong:** when a day-part word precedes the time, the hour must be 12-hour; a 24-hour hour makes `_apply_part` return `None` and the time is skipped entirely. A correct answer written "शाम 18:30" or "evening 18:30" is not recognised, so `value:departure=18:30_not_stated` fails a correct answer. Affects every task in `VALUE_CHECKS` with a time (T07, T08, T12, T31, T44, T51, T52, T55-T57, T64, T65) in hi/hinglish/mr/gu.
- **Evidence:** `times_in("शाम 18:30 बजे")`, `("रात 23:30")`, `("સાંજે 18:30")`, `("सुबह 13:00")`, `("evening 18:30")` all return `set()`; `times_in("18:30")` returns `{'18:30'}`; `times_in("रात्री 8:20")` returns `{20:20}` (the 12-hour case works).
- **Proposed fix:** when `h >= 13` (or `h == 0`) with a day-part word, accept the hour as 24-hour; keep the current conversion for `1..12`. Add tests for each language.
- **Frozen/history:** no frozen data; it only makes the scorer more lenient for correct answers. The two 3B runs would need a re-score (not a re-run) if the numbers are to be comparable; `analysis/results/` must not be edited, write new folders.

### I-03: Gujarati missing from structured-value canonicalizers

### I-04: `context_overflow` is unscored, which biases comparisons
- **File:** `agents/ollama_adapter.py:157-162` (raises non-retryable `ProviderError('context_overflow')`), `evaluation/scorer.py:28` (`provider_error` is `NOT_SCORED`), `evaluation/run_pilot.py` (`--resume` re-runs it, same result).
- **What is wrong:** an overflow is caused by the model's own behaviour (looping tool calls until the history is large), but the row is excluded from scoring. Models that loop more lose more hard items, so denominators differ across models and the comparison is biased in favour of the looping model. With 8192 tokens this will recur: the Qwen 2.5 3B run has `T41_hinglish` at 7,134 input tokens; the Llama 3.2 3B run has a maximum of 1,386.
- **Evidence:** read-only stats of `runs/local_qwen25_3b_full_20261013T222957Z.jsonl`: statuses `completed 145, malformed_output 43, step_limit_exceeded 11, provider_error 1` (`context_overflow`), top max input tokens 7134, 5155, 4867, 4081. Llama: 200 completed, max input 1,386.
- **Proposed fix (choose one, needs your decision):** (a) keep the 8192 window for all models and score `context_overflow` as a model failure (new status, counted in the denominator); or (b) raise `num_ctx` to e.g. 16384 for every local model including a re-run of the two 3B models. Memory is not the constraint here (A30 24 GB). Either way the 3B baselines are no longer directly comparable unless re-run or re-scored.
- **Frozen/history:** touches historical results only through comparability; do not edit the old runs.

### I-05: Ollama thinking models (Qwen3, gpt-oss, DeepSeek-R1 style)
- **File:** `agents/ollama_adapter.py:134-138` (`_options`, no `think`), `:164-170` (empty content + tokens -> `unparsed_model_output`), `:192-196` (assistant history keeps only `content` and `tool_calls`).
- **What is wrong:** (1) there is no `think` setting, so thinking behaviour is whatever the Ollama default is for the model and cannot be pinned or disabled (gpt-oss cannot be disabled, only low/medium/high); (2) `num_predict = max_tokens = 1024` also covers the thinking tokens, so a long thought ends with `done_reason: length`, empty content and no tool call; (3) that case is reported as `malformed_output` / `unparsed_model_output` (a model failure) with a message about "tool-call parser", which is misleading; (4) the `thinking` field is not passed back in later turns, which Ollama recommends for tool-calling loops with thinking models. Not relevant to Qwen 2.5 / Llama 3.1, relevant if any Qwen3, gpt-oss, DeepSeek-R1 or similar is added.
- **Evidence:** mock Ollama server (scratchpad script): a reply with `thinking` + `tool_calls` parses (thinking ignored); a reply with 5,000 chars of `thinking`, empty content, `done_reason: length`, `eval_count 1024` raises `ModelOutputError unparsed_model_output`; the stored history roles show no `thinking` key.
- **Proposed fix:** optional `think` config value (true/false/"low"/"medium"/"high") passed through and recorded in `settings()`; echo `thinking` back in the history; classify `done_reason == "length"` with empty content as its own model failure (`output_truncated`); record `thinking` in the raw log. Adding `think` to the identical-settings test keys.
- **Frozen/history:** no. Only affects new models; existing `local_*` entries unchanged if `think` stays unset.

### I-06: Ollama flattens the `time_window` schema
- **File:** `agents/ollama_adapter.py:23-24` (docstring records that Ollama drops `$defs`/`$ref`/`additionalProperties`, so `time_window` becomes `anyOf [{}, null]`); `environment/schemas.py` + `railway_env.tool_specs()` (the schema uses `$defs`/`$ref` for `TimeWindow`).
- **What is wrong:** the model sees `time_window` as an untyped optional value. Only the tool description mentions `{start, end}`. Models differ in how well they guess the shape from the description, so tool-call accuracy partly measures schema handling in Ollama, not the model.
- **Evidence:** `search_trains` schema contains `"time_window": {"anyOf": [{"$ref": "#/$defs/TimeWindow"}, {"type": "null"}]}` with `TimeWindow` under `$defs`; the adapter sends `t["parameters"]` unchanged. The flattening is recorded from Ollama 0.40.3 in the adapter docstring; I did not re-verify it on 0.40.13 (no server calls allowed).
- **Proposed fix:** inline `$ref`/`$defs` in the adapter only (`_convert_tools`), so `TOOL_SCHEMA_SHA256` (computed from `tool_specs()`) is unchanged. Verify what the server actually receives once a smoke run is approved.
- **Frozen/history:** does not change benchmark data, but the 3B results were produced with the flattened schema, so they are not strictly comparable to runs with the inlined one unless the 3B models are re-run.

### I-07: no preflight for tool support or Modelfile parameters
- **File:** `agents/ollama_adapter.py:112-126` (`_load_model_info` reads `/api/tags` only).
- **What is wrong:** (1) a model without tool support returns HTTP 400 on every request; every item becomes a non-retryable `provider_error` (unscored) after a full run of requests; (2) Modelfile defaults (`repeat_penalty`, `top_k`, `top_p`, stop tokens) are not pinned or recorded. At temperature 0 `top_k/top_p` are irrelevant but `repeat_penalty` is not, and defaults differ per model family, so "identical settings" is not fully true.
- **Evidence:** mock: HTTP 400 `"... does not support tools"` -> `ProviderError bad_request` (non-retryable). `settings()` records only temperature, seed, num_ctx, max_tokens, keep_alive.
- **Proposed fix:** at `start()` (or in `prerun_snapshot`) call `/api/show`, require the `tools` capability, record `parameters`/template hash in the settings, and fail fast with a clear message. Optionally pin `repeat_penalty` explicitly for all models (decision for you).
- **Frozen/history:** no.

### I-08: T38 Marathi (and weaker Hindi/Hinglish) wording
- **File:** `benchmark/languages/mr.jsonl:38` (`दुसऱ्या सर्वात स्वस्त ट्रेनमध्ये`), source `benchmark/batch_t26_t50.py`; Hindi `hi.jsonl:38` (`सबसे सस्ती दूसरी ट्रेन`), Hinglish `hinglish.jsonl:38` (`sabse sasti dusri train`).
- **What is wrong:** gold is BTB123 (the cheapest *other* train). On ADI->MMCT 3A the fares are BTB123 = 1125, BTB103 = 2495 (sold out, the named train), BTB101 = 3135. The Marathi phrase reads "second-cheapest", which is BTB101 if the sold-out train is excluded, so a correct Marathi reading books the wrong train by gold. Hindi/Hinglish put "दूसरी / dusri" ("other" or "second") after "cheapest", which is clearer but still ambiguous. English ("cheapest other train") and Gujarati (`બીજી ટ્રેનોમાંથી સૌથી સસ્તી`, "cheapest among the other trains") are fine.
- **Evidence:** fares and availability read from the environment; the language audit for T38 already flags `constraint_risk` for all three.
- **Proposed fix:** change Marathi to "इतर गाड्यांपैकी सर्वात स्वस्त" style wording (needs a native review), and consider "बाकी ट्रेनों में सबसे सस्ती" for Hindi. This requires changing frozen text, so: edit `batch_t26_t50.py`, rebuild, update `FROZEN_T01_T50_LANG_SHA256` on purpose, re-record the human review for the changed items.
- **Frozen/history:** **yes, frozen and human-reviewed (mr). Not to be changed without your approval.** The Marathi results of the 3B runs for T38 are affected.

### I-09: T54 `requested_passengers` contract vs scorer
- **File:** `evaluation/final_answer.py:40+` (`"requested_passengers": ["<passenger name as given by the user>", ...]`), `evaluation/scorer.py:364-367` (set equality with the Latin spec name).
- **What is wrong:** in T54 hi/mr/gu the user writes the passenger in native script (`रवि पटेल`, `રવિ પટેલ`) and `book_ticket` needs Latin. The contract says to copy the name "as given by the user". A model that follows it writes the native name and fails `final_answer:wrong_requested_passengers`; only a model that transliterates to exactly `Ravi Patel` passes. The instruction and the scorer disagree.
- **Evidence:** `semantic_tasks.json` T54 params `passenger: "Ravi Patel"`, `passenger_script_forms {hi, mr, gu}`; query text as shown; scorer compares `canon_passenger` of spec names.
- **Proposed fix:** either accept the declared `passenger_script_forms` in the scorer for T54, or change the contract text to "passenger name in Latin letters". The first option does not change the prompt hash, the second does.
- **Frozen/history:** T54 is not in the frozen T01-T50 range. Changing the contract text changes `system_prompt_sha256`, which breaks hash equality with the 3B runs (they never ran T51-T75, so only provenance comparison is affected).

### I-10: zero-call tasks and the null baseline
- **File:** `benchmark/gold_labels.json` (generated; T09, T19, T29, T30, T36, T37, T45, T46, T67, T69, T74 have no non-optional required calls; documented in `benchmark/COVERAGE_REPORT.md:30`).

The Qwen 2.5 3B and Llama 3.2 3B full runs have `task_success` 3/200 (1.5%), so both are below this trivial baseline. T29/T30/T45 (`cannot_complete`) are also passable by refusing blindly.
- **Evidence:** mutation test: "no tool calls + ideal final answer" passes exactly those 11 tasks; counts of gold statuses: success 51, cannot_complete 15, needs_clarification 9.
- **Proposed fix:** do not change gold (frozen). Add a "null baseline" row (no tools, constant status) to `analysis/` reports so scores are read against it, and report accuracy separately for tasks that need tools.
- **Frozen/history:** no change to frozen data.

### I-11: free-text number checks can match unrelated numbers
- **File:** `evaluation/scorer.py:305-308` (`_value_found`), `evaluation/canonical.py:107-119` (`numbers_in`), table `VALUE_CHECKS` (`scorer.py:34-64`).
- **What is wrong:** a number check passes if the integer appears anywhere in the reply (including dates and counts). Small gold values make accidental passes likely: T02 17, T26 2, T58 2, T51 4, T50 0. Also `times_in` reads "₹14.50" as 14:50 (the `.` separator).
- **Evidence:** `numbers_in("Booked on 9 October, 2 seats, fare 1,125. BK0001 3A")` returns `{9, 2, 1125}`; `times_in("₹14.50")` returns `{'14:50'}`. The mutation test shows the check is not skippable (a reply with no value fails), so the risk is a wrong answer plus an unrelated matching number.
- **Proposed fix:** move small-valued facts (T26, T50, T51, T58, T02) to structured `answer_values`, or require the number to appear next to its label; drop `.` as a time separator unless followed by AM/PM. Contract changes alter the system-prompt hash.
- **Frozen/history:** T01-T50 scorer tables are not hash-frozen (only spec/gold/language); changes to the scorer alter comparability with the 3B scores for T02, T26, T50, so re-score the old runs into new folders.

## 10. Follow-up 3 (2026-11-24): one yes/no rule for all five languages, version 2.0.2

- **Problem:** after `25e2476` Gujarati yes/no was read inside sentences while en, hinglish, hi and mr matched whole values only, which would bias the cross-language comparison.
