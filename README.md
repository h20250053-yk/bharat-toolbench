# BharatToolBench

A controlled benchmark for measuring how reliably LLM agents use tools in Indian digital-service tasks,
and how that reliability changes with the **language of the request** (English, Hinglish, Hindi, Marathi, Gujarati).
The testbed is a **simulated** railway-booking service: no real IRCTC, no payments, no Aadhaar, no real data.

Core idea: one *semantic task* has five language variants that share the same environment state, constraints and
programmatic gold label, so language is the only thing that varies. Correctness is judged from tool calls and the
final environment state, never by an LLM judge.

## Summary

BharatToolBench has 75 semantic tasks, each written in five languages (English, Hinglish, Hindi, Marathi, Gujarati), so 375 items per model.
Every item runs against a deterministic, **synthetic** railway environment with six tools; gold answers are generated by solvers, and scoring
uses the final environment state, the final answer block and the tool-call process (no LLM judge). Version 2.1.0 (tag `v2.1.0-data`).
Eight open-weight models were evaluated locally with Ollama 0.40.18 on one GPU, with identical settings (temperature 0, seed 42, `num_ctx` 16384, `max_tokens` 2048, 8 turns).
The headline score is **lenient** (format recovery only, every recovery recorded, prose never turned into an answer); the **strict** score is reported next to it.
All results, tables, statistics and figures are in [`RESULTS.md`](RESULTS.md) and `analysis/`; tool-selection metrics are defined in [`METRICS.md`](METRICS.md).
Read the caveats in `RESULTS.md` (one model is marked unreliable because of a serving problem; several models score below a never-use-a-tool baseline).

## Reproduce the results

The run files for the eight models are in `runs/*_full_20261124T105853Z*` (with manifests and pre-run snapshots) and the per-run summaries in `analysis/results/`.
Every number, table and figure is rebuilt from those files and `benchmark/gold_labels.json` with one command (needs numpy, scipy, matplotlib, Pillow with Raqm; Graphviz `dot` for the pipeline diagram):

```bash
PYTHONPATH=. python -m analysis.build_results --status runs/full_phase_20261124T105853Z.status.json
```

Outputs: `RESULTS.md`, `analysis/results_final/` (CSV/JSON), `analysis/figures_final/` (figures as PNG and PDF, `captions.md`, `examples.md`, LaTeX tables, the animated pipeline GIF).
Checks: `python -m benchmark.validate_tasks`, `python -m evaluation.smoke`, `python -m pytest -q`.
To re-run a model locally (needs an Ollama server >= 0.40.18) see `LOCAL_MODELS.md`. No API keys are needed or stored.

## How the environment works

- **Deterministic simulation, no live IRCTC connection.** Nothing here queries or reflects any real booking system.
- **Real-world-anchored stations**: 10 stations with real names, canonical codes (e.g. Mumbai Central = `MMCT`), cities and
  states (two are in Delhi: `NDLS`, `NZM`, so "Delhi" is genuinely ambiguous).
- **Synthetic train services**: 30 fictional trains, IDs `BTB101`-`BTB130`, fictional names. They are **NOT actual
  operating Indian Railways services**; schedules and distances are plausibility fixtures, not the real timetable.
- **Synthetic fares**: deterministic per-km rule by train type and class (documented in `benchmark/data_provenance.md`;
  generated by `environment/build_world.py`). Not live fares.
- **Synthetic availability**: fixed baseline seats per (train, class), including low and sold-out cases. Not live.
- **Reset before every benchmark task**: call `env.reset()` so availability, bookings and the booking counter return to baseline.
- **Classes**: `3A`, `2A`, `SL`, `CC`. Each train offers a subset. Fares (INR) and baseline seats are stored in `trains.json`;
  some classes are sold out and some have 1-3 seats, to support recovery and booking-conflict tasks later.
- **Time**: the "current time" is pinned to **2026-10-05 09:00 IST** (`config/benchmark.yaml`). The system clock is never read.
  Dates are `YYYY-MM-DD`, times 24-hour `HH:MM`. Date in the past => `PAST_DATE`. On the reference date, trains
  departing at or before 09:00 are not returned. `operating_days` refers to the weekday the train leaves its
  *origin*; searching from a later stop uses the correct origin date.
- **State**: immutable fixtures plus mutable `availability`, `bookings`, `next_booking_seq`. `env.reset()` restores the
  exact baseline; `env.snapshot()` / `env.state_hash()` expose state for tests and (later) scoring. Failed calls never mutate state.
- **No randomness anywhere.** Booking IDs are `BK0001, BK0002, ...`; PNRs are a SHA-256 function of the booking inputs and sequence number.
- **Frozen-contract simplifications**: availability and bookings are per (train, class), not per date, and fare is per
  (train, class) for the whole journey, because the six tool signatures take no date or station arguments there.
- **Errors** are structured results, never exceptions: `{"ok": false, "data": null, "error": {"code": ..., "message": ...}}`.
  Zero trains found is a *successful* empty result (`count: 0`), not an error.

## The six tools

| Tool | Input | Success data | Error codes |
|---|---|---|---|
| `resolve_station` | `name` | `query, ambiguous, candidates[{code,name,city}]` | `STATION_NOT_FOUND` |
| `search_trains` | `source, destination` (codes), `date`, `time_window?{start,end}` | `count, trains[{train_id, train_name, departure, arrival, arrival_day_offset, duration_minutes, classes}]` | `INVALID_STATION, SAME_STATION, INVALID_DATE, PAST_DATE, INVALID_TIME_WINDOW` |
| `get_train_details` | `train_id` | name, type, operating days, classes, distance, stops with times | `INVALID_TRAIN` |
| `check_availability` | `train_id, travel_class` | `seats_available, status` (`AVAILABLE`/`SOLD_OUT`) | `INVALID_TRAIN, INVALID_CLASS, CLASS_NOT_OFFERED` |
| `get_fare` | `train_id, travel_class` | `fare_inr, currency` | same as above |
| `book_ticket` (**mutates state**) | `train_id, travel_class, passenger` | `booking_id, pnr, train_id, travel_class, passenger, fare_inr, status` | above + `INVALID_PASSENGER, DUPLICATE_BOOKING, SOLD_OUT` |

Booking validation order: train, class, class-offered, passenger, duplicate, availability. A duplicate is the same
(train, class, passenger name, case/whitespace-insensitive). `resolve_station` is exact match after deterministic
normalization (casefold, punctuation, Devanagari nukta) - deliberately no fuzzy matching. Generic entry point for the
future runner: `env.call(tool_name, arguments_dict)` (validates against the Pydantic input schema; extra, missing or
wrong-typed arguments give `INVALID_ARGUMENTS`). `tool_specs()` returns provider-neutral name/description/JSON-schema.

## Pilot tasks (T01-T05; English source + language variants)

| File | Role |
|---|---|
| `benchmark/semantic_tasks.json` | language-independent spec: goal, constraints, allowed tools, solver params, final-answer requirements, initial-state assumptions + machine-checked initial-state facts |
| `benchmark/languages/en.jsonl` | the English prompts (one `BenchmarkItem` per task, `review_status: draft`) |
| `benchmark/build_gold.py` | **generates** `benchmark/gold_labels.json` by solving each spec against the environment (never hand-edited, never LLM-made) |
| `benchmark/gold_labels.json` | required calls, dependency edges, final state/answer, expected env diff, env hashes |
| `benchmark/validate_tasks.py` | validator incl. an independent oracle that recomputes answers from the raw fixture JSON |

```bash
python -m benchmark.build_gold                # regenerate gold for T01-T75 (must be byte-identical on rerun)
python -m benchmark.build_language_variants   # (re)write language rows; frozen pilot rows are copied byte-for-byte
python -m benchmark.build_language_audit      # pilot (20) + T06-T15 (40) + T16-T25 (40) + T26-T50 (100) + T51-T75 (100) audits
python -m benchmark.coverage_report           # coverage / tool-use / difficulty metrics -> benchmark/COVERAGE_REPORT.md
python -m benchmark.semantic_overlap          # semantic-duplicate check over all tasks
python -m benchmark.validate_tasks            # validate all 75 tasks x 5 languages = 375 items (includes the duplicate check)
```
Gold arg conventions: `required_args` are exact canonical values (station codes, ISO dates, HH:MM, class enum, train ids);
`resolve_station.name` is language-specific, so its gold is a matcher `{"resolves_to": "<code>"}`;
`arg_alternatives` lists extra accepted values (e.g. omitting `time_window`); a dependency edge `a -> b` means call `b` needs the output of call `a`.

Batch additions (backward compatible): `expected_error` on a required call (serialised only when set), the
`{"resolves_ambiguous": [...]}` matcher, `optional` calls excluded from `min_calls`, multi-booking `booking_ids`
(see `benchmark/BATCH_T06_T15.md`).

Explicit prohibitions: a spec may list `prohibited_actions` (`tool`, optional arg `match`, the exact `prompt_phrase` that creates it, `reason`);
gold carries them plus a derived `forbidden_tools`. Used only where the user explicitly forbids something (pilot: T03 "Don't book anything",
T05 "only if seats are available" / "don't book any other class or train"). Arbitrary extra read-only calls are never prohibited.
The scorer that consumes this is a later phase.

Linux (the GPU server), with a project-local venv:

```bash
python3 -m venv .venv                # first time only
source .venv/bin/activate
pip install -r requirements.txt
python -m pytest -q -k "not nemotron and not openrouter"   # ~769 passed
```

## Run the vertical-slice demo (no LLM)

```bash
python run.py demo
```
A hard-coded script (not an agent) runs resolve_station, search_trains, get_train_details, check_availability,
get_fare, book_ticket, re-checks availability, then resets and confirms the state hash matches the start.

## Evaluation commands

Pilot: `python -m evaluation.run_pilot --model primary_a --split pilot` and `python -m evaluation.run_pilot --model primary_b --split pilot`.

Splits: `pilot` = T01-T05, `midsem` = T01-T50 (the mid-sem pilot study), `full` = every task in the spec (T01-T75).

Resume an interrupted run with the same JSONL file using `--resume`. Keep `fallback_b` as a separate run; never mix fallback rows into a primary-B run.

Report: `python -m analysis.pilot_report runs/<file>.jsonl`

Offline smoke: `python -m evaluation.smoke`

## Planned architecture

Task -> Runner -> Model Adapter -> Canonical Tool Call -> Railway Environment -> Observation -> Model -> Trajectory -> Scorer -> Metrics.
The environment layer is deterministic and provider-neutral; provider SDKs live exclusively in `agents/` adapters.
